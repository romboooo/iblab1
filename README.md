# Защищённый REST API

Учебный backend на Python и Flask: вход по паролю с выдачей JWT, закрытые пользовательские заметки в SQLite, защита SQL-запросов и автоматические проверки Bandit и pip-audit в GitHub Actions.

## Запуск

Нужен Python 3.10 или новее.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
export JWT_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')"
flask --app app:create_app create-user student
flask --app app:create_app run --host 127.0.0.1
```

Команда `create-user` запросит пароль без отображения ввода и подтверждение. Пароль должен содержать от 12 до 128 символов. База по умолчанию создаётся в `instance/api.sqlite3`; путь можно задать переменной `DATABASE_PATH`. Секрет JWT не имеет значения по умолчанию: задайте случайный секрет не короче 32 байт и храните его в Secrets репозитория для развёртывания.

## API

Все тела запросов и ответов — JSON. Для закрытых методов передавайте заголовок `Authorization: Bearer <токен>`.

| Метод и путь | Доступ | Назначение |
| --- | --- | --- |
| `POST /auth/login` | публичный | Проверяет логин и пароль, возвращает JWT на 15 минут |
| `GET /api/data` | JWT | Возвращает заметки текущего пользователя |
| `POST /api/data` | JWT | Создаёт заметку текущего пользователя |
| `GET /health` | публичный | Проверка доступности сервиса |

Примеры для запущенного сервера:

```bash
curl -sS http://127.0.0.1:5000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"student","password":"ЗаменитеНаВашПароль123!"}'
```

Скопируйте значение `access_token` из ответа и используйте его в запросах:

```bash
curl -i http://127.0.0.1:5000/api/data

curl -sS http://127.0.0.1:5000/api/data \
  -H 'Authorization: Bearer <access_token>'

curl -sS http://127.0.0.1:5000/api/data \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Первая заметка","content":"Текст заметки"}'
```

Без токена `/api/data` отвечает `401 Unauthorized`. Ошибка входа возвращается одинаково для неизвестного пользователя и неверного пароля.

## Реализованные меры защиты

- **SQL-инъекции:** все значения в `SELECT`, `INSERT` и запросе чтения новой записи передаются отдельно через параметры SQLite (`?`). Пользовательские строки не добавляются в SQL-код конкатенацией. Запросы выбирают записи по `user_id` из проверенного JWT, поэтому пользователь не может прочитать чужие заметки.
- **XSS:** API отвечает JSON, не формирует HTML и экранирует пользовательские `title` и `content` через `html.escape` при выдаче. Клиентскому интерфейсу всё равно следует вставлять значения как текст (`textContent`), а не как HTML.
- **Аутентификация:** пароли хэшируются Argon2id через `argon2-cffi`; в базе хранится только хэш. Вход выдаёт подписанный HS256 JWT с `sub`, `iat`, `nbf`, `exp`, `iss` и `aud`. Middleware проверяет подпись разрешённым алгоритмом, обязательные claims, издателя, аудиторию и срок действия. Секрет берётся из `JWT_SECRET_KEY`; слабый или отсутствующий секрет не допускается.
- **Дополнительно:** ограничен размер JSON-запроса, неожиданные поля создания заметки отклоняются, ошибки входа не раскрывают существование учётной записи, а ответы получают `nosniff`, `frame-ancestors`, `no-store` и другие защитные заголовки.

## Тесты и CI/CD

Локально запустить проверки можно командами:

```bash
python -m unittest discover -s tests -v
bandit -r app.py tests -f screen -l -i
pip-audit -r requirements-dev.txt --progress-spinner off
```

Workflow [`.github/workflows/ci.yml`](.github/workflows/ci.yml) запускается при push в `main` и для pull request в `main`. Он выполняет интеграционные тесты, Bandit SAST и pip-audit SCA. При любой найденной уязвимости шаг проверки завершается ошибкой. JSON-отчёты обоих сканеров прикладываются к каждому запуску в артефакт `security-reports`.

Запуски: [GitHub Actions](https://github.com/romboooo/iblab1/actions/workflows/ci.yml). После первого успешного запуска здесь можно закрепить ссылку на конкретный run и скриншоты отчётов из него.

## Контрольные вопросы

1. **Почему bcrypt/Argon2 предпочтительнее SHA-256 для паролей?** Это медленные алгоритмы с солью и настраиваемой стоимостью вычислений. Перебор украденной базы обходится дороже, а одинаковые пароли получают разные хэши. SHA-256 очень быстр и поэтому позволяет проверять намного больше вариантов в секунду.
2. **Разница между SAST и DAST?** SAST анализирует исходный код или байткод без запуска приложения. DAST проверяет уже работающий сервис снаружи, отправляя запросы и наблюдая за ответами.
3. **Как работает JWT?** Токен содержит закодированные заголовок и claims с идентификатором пользователя и сроком действия, а также подпись. Сервер пересчитывает подпись доверенным секретом и проверяет срок, издателя и аудиторию; содержимое JWT не зашифровано, поэтому в него нельзя помещать пароль или другие секреты.
4. **Чем опасен отказ от аудита зависимостей?** Уязвимость сторонней библиотеки становится уязвимостью приложения, даже если собственный код безопасен. Без SCA команда может не знать о CVE, уязвимом транзитивном пакете или необходимости обновления.

## Ограничения учебного примера

Для реального развёртывания добавьте распределённое ограничение частоты входа, управление секретами и ротацию ключей, HTTPS за production WSGI-сервером, резервное копирование и миграции базы данных. Flask dev-сервер предназначен только для локальной проверки.
